## 1. 背景与动机

IAC-P 最初定位为"胶水层"——在 Create、Sable、Offroad 等现有模组之间编写连接代码，让物理结构可以被驾驶和控制。随着需求加深，项目自发地构建了越来越多超越"胶水"范畴的基础设施：

- `AffiliationRegistry` — 归属与所有权运行时索引
- `ComponentRegistry` — 功能部件 O(1) 查询
- `SmartKeyHandler` — 输入映射抽象
- `SubLevelScanner` / `SubLevelUtil` — SubLevel 工具集
- `VehicleDebugOverlay` — 调试监控

这些设施说明一个事实：**当"胶水"覆盖的厚度和广度达到一定程度，它就不再是胶水，而是变成了一个薄层引擎。** 与其凭感觉拼凑，不如主动参考成熟轻量级游戏引擎的设计，按需选择性地构建基础设施。

### 什么是"轻量级游戏引擎"？

在本文语境下，轻量级游戏引擎指：

> 提供游戏开发通用基础设施，但不强加庞大框架的中间层——通常包含实体管理、输入、事件、配置、资源、调试等机制，让开发者专注于具体玩法逻辑，而非重复搭建支撑系统。

**不是**：
- 不替代 Minecraft 的渲染/网络/物理（这些由原版 + Sable + NeoForge 提供）
- 不替代 NeoForge 的 Mod 加载系统
- 不追求通用性，只服务"载具工坊"这一个游戏类型

**是**：
- 让新功能按模板添加（而不是每次重写一套新 BlockEntity）
- 让跨部件协调有统一路径（而不是每次重写一遍 ComponentRegistry 查表）
- 让游戏参数可配置（而不是改编译时常量 → 重启游戏）

## 2. 轻量级游戏引擎的八个基础设施领域

### 2.1 实体-组件架构

#### 引擎标配

游戏引擎的核心模式——实体（Entity）是空壳，由组件（Component）组合出行为，系统（System）负责逻辑。

```
Entity (空 ID)
 ├─ TransformComponent (位置)
 ├─ MeshComponent (渲染)
 ├─ RigidBodyComponent (物理)
 └─ VehicleInputComponent (输入)
         ↓
VehicleSystem.onTick():
  FOR EACH entity WITH (Transform + RigidBody + VehicleInput):
    读取 VehicleInput → 施加 RigidBody 力
```

关键特征：
- **数据与逻辑分离**：Entity/Component 纯数据，System 纯逻辑
- **按需查询**：System 只处理有所需组件的实体
- **无继承**：行为由组件组合决定，而非类继承

#### IAC-P 现状

你们已经在 `docs/ai/01-ecs-architecture.md` 和 `control_architecture.md` 中设计了一套**System/Part 架构**（原 `01-core-architecture.md`，包已重命名为 `ecs`）：

```
Minecraft Tick ──── VehicleSystemDispatcher
                        ├─ VehicleTickSystem       (20Hz 逻辑)
                        ├─ VehiclePhysicsSystem    (物理步进前)
                        └─ VehicleClientSystem     (客户端)
                               │
                               ▼
                        VehicleSystemRegistry
                        (collectParts + 三个 List)
                               │
                               ▼
                        PartBlockEntity (instanceof 分发)
```

**尚未实现的部分**：
- `VehicleSystemRegistry` 的类定义
- `VehicleSystemDispatcher` 的事件桥接
- `PartBlockEntity` 基类
- 任意一个真实的 System 实现

**当前实际模式**（等待架构落地前）：

```
BlockEntity (状态 + 逻辑 + 渲染 + 网络)
  └─ SuspensionTestBlockEntity: 物理计算、控制输入、NBT、网络同步
  └─ CockpitBlockEntity: 发动机、变速箱、智能映射、NBT
  └─ ShotGunBlockEntity: 瞄准、开火、动画状态
```

每个 BE 是"自包含小宇宙"，跨 BE 协调通过 `ComponentRegistry` 查表或直接缓存引用。

### 2.2 消息/事件总线

#### 引擎标配

除了全局事件，引擎通常提供**实体级别**或**系统间**的消息通道：

```
vehicleEventBus.post(new PartDestroyedEvent(partId));
    → SuspensionSystem 收到 → 重新计算载荷分布
    → AffiliationSystem 收到 → 更新部件状态
    → HUDSystem 收到 → 显示部件损坏图标
```

#### IAC-P 现状

| 通信需求 | 当前做法 | 评价 |
|---------|---------|------|
| BE → BE（同 SubLevel） | 扫描 SubLevel 直接调用 | O(n) 扫描，但够用 |
| BE → BE（跨 SubLevel） | ComponentRegistry 查表 | ✅ 设计良好 |
| System → System | NeoForge 全局事件总线 | 缺乏车辆级别过滤 |
| 客户端 → 服务端 | CustomPacketPayload | ✅ 17 种 packet |

**现状总结**：没有车辆内部的消息总线，但当前复杂度下也不需要。跨 BE 通信靠 `ComponentRegistry` + 直接方法调用已够用。

### 2.3 输入抽象层

#### 引擎标配

游戏引擎不会让开发者直接查按键状态。而是定义 **Action**（抽象游戏行为），由玩家或配置将物理按键映射到 Action：

```
Action 定义:    "move_forward"  (范围 -1.0 ~ 1.0)
                    ↕ 映射层
物理输入:       W 键 / 左摇杆上推 / 手柄右扳机
```

System 只读 Action 值，不关心具体输入设备。

#### IAC-P 现状

你们的 `SmartKeyHandler` + 智能映射系统已经非常接近这个模式：

```
原始按键 (W/A/S/D/Q/E/空格)
    │  SmartKeyHandler 转译
    ▼
5 个布尔 Action: {throttleForward, throttleBackward, left, right, brake}
    │  序列化到 VehicleControlC2SPacket
    ▼
服务端 BlockEntity.applyControlInput()
```

差距：
- Action 数量固定为 5，且全为布尔值
- 没有开放给数据包/脚本自定义

### 2.4 数据驱动配置

#### 引擎标配

游戏数据（物理参数、武器属性）定义在数据文件中，而非代码编译时常量。高级引擎支持热加载。

```
data/vehicles/light_truck.json:
{
  "engine": { "torqueMax": 5.0, "idleRpm": 800, "maxRpm": 6000 },
  "transmission": { "gears": [4.0, 2.5, 1.6, 1.2, 1.0], "finalDrive": 14.0 },
  "suspension": { "stiffness": 400, "damping": 40, "rideHeight": 0.6 }
}
```

#### IAC-P 现状

```
编译时常量（需重启）:
  SuspensionConstants.java: SPRING_STIFFNESS=400, RIDE_HEIGHT=0.6
  PowertrainConstants.java: GEAR_RATIOS, TORQUE_MIN=4.0, TORQUE_MAX=5.0

ModConfigSpec（运行时改，需保存）:
  Config.java: 相机距离、瞄准偏移

数据驱动（已有雏形）:
  skill/car_mode.json: WASD 映射规则
```

**核心问题**：不同车型无法有不同的物理参数。所有车辆共享同一套 `SuspensionConstants`。

### 2.5 物理抽象层

#### 引擎标配

引擎在原生物理 API 之上提供一层游戏友好的封装：

```
物理引擎层 (Bullet / PhysX / Rapier)
    ↑
引擎物理抽象: RigidBody.AddForce(Vector3), Physics.Raycast()
    ↑
游戏代码: 只关心 "施加驱动力"，不关心力空间变换和质量查询
```

#### IAC-P 现状

你们直接调 Sable Rust API：

```java
RigidBodyHandle.of(subLevel).addForce(forceTotal, true);
```

Sable 的 API 本身设计已较干净，问题在于你们每次都要：
1. 查 SubLevel → `logicalPose()` → 变换力作用点
2. 查质量 → `MassData.getMass()`
3. 算力 → 构建 `ForceTotal`
4. 施加 → `RigidBodyHandle.addForce()`

这些步骤散布在各个 BE 的 `physicsTick()` 中，重复且容易出错。

### 2.6 资源/资产管理

#### 引擎标配

统一资源加载接口，支持：
- 异步加载
- 引用计数（资源自动卸载）
- 热重载（改文件后游戏内即时生效）

#### IAC-P 现状

| 资源类型 | 管理方式 |
|---------|---------|
| GeckoLib 模型 | 约定路径自动加载 |
| 音效 | NeoForge ModSounds 注册 |
| 纹理 | 原版 ResourceLocation |
| 特效 | 尚未实现（占位符主义） |

你们的设计哲学明确"不做官方的音效/特效/纹理包，做素材包导入框架交给社区"。这个框架目前还在待办中（⭐⭐⭐）。

### 2.7 序列化一致性

#### 引擎标配

场景/预制体有统一保存加载机制，不需要每个类型自己写 NBT 逻辑。

#### IAC-P 现状

每个 BE 自己实现 `saveAdditional()` / `loadAdditional()` / `getUpdatePacket()` / `handleUpdateTag()`。这是 Minecraft 体系本身的限制，不算 IAC-P 特有的问题。

### 2.8 性能分析/调试工具

#### 引擎标配

内置 Profiler，可看每帧/每 tick 每个 System 耗时。

#### IAC-P 现状

| 工具 | 实现 |
|------|------|
| 调试覆盖层 | `VehicleDebugOverlay` — RPM/速度/摩擦预算 |
| 慢查询日志 | `AffiliationRegistry` 嵌入纳秒计时 |
| 性能报告 | `5.5-性能分析报告/` 文档分析 |

## 3. 现状全景评估

| # | 基础设施领域 | 成熟度 | 优先级 | 一句话结论 |
|:-:|------------|:-----:|:------:|-----------|
| 1 | **System/Part 架构** | 🟡 设计完成，未实现 | **最高** | 接口已定，只差写类 |
| 2 | **运行时组件索引** | ✅ 成熟 | — | ComponentRegistry 设计优秀，保持 |
| 3 | **归属/所有权** | ✅ 成熟 | — | AffiliationRegistry 包含了 |
| 4 | **消息/事件总线** | 🟢 够用 | 低 | NeoForge 总线 + ComponentRegistry 查表暂时够 |
| 5 | **输入抽象** | ✅ 接近成熟 | 低 | SmartKeyHandler 已接近 Action 系统 |
| 6 | **数据驱动配置** | 🟡 部分数据化 | **高** | 物理参数固化在常量中，限制扩展 |
| 7 | **物理抽象** | 🟢 够用 | 中 | Sable API 干净，但重复代码多 |
| 8 | **资源管理** | 🟢 够用 | 中 | 社区素材包框架是远期 |
| 9 | **序列化** | 🟢 够用 | 低 | Minecraft 体系限制 |

**核心判断**：

> 项目当前最需要的不是"新建什么"，而是**把已有的设计文档变成代码**——System/Part 架构的接口已经想清楚了，编译成 Java 类的工作量不大，但能立刻改变整个项目的架构感知。

### 4.2 中期（1-2 月）

#### 行动 4：TireType 注册表 + 物理参数数据化

从"所有轮胎共用一套物理常数"到"不同轮胎有不同的刚度/阻尼/滚动阻力"。

**切入点**：Offroad 已经提供了 `TireLike` 数据组件（`OffroadDataComponents.TIRE`），你们只需要在上面加一层物理参数映射：

```java
// 可能的方案
public class TirePhysicsRegistry {
    // 按 TireLike 的 item 或 tag 映射物理参数
    static final Map<Item, TirePhysicsParams> REGISTRY = ...;

    public record TirePhysicsParams(
        double stiffness,    // 弹簧刚度 N/m
        double damping,      // 阻尼
        double rollingResistance, // 滚动阻力系数
        double maxPressure   // 最大胎压 Pa
    ) {}
}
```

**为什么优先做这个**：这是"数据驱动"最自然的切入点——轮胎在游戏中已经是物品（Item）了，不同物品有不同的属性符合直觉。

#### 行动 5：抽第一个真实 System：WeaponAimSystem

瞄准逻辑是**天然跨 Part 协调**的场景：需要知道所有炮塔的位置、所有武器的状态、目标点的位置。最适合作为第一个 System。

```
WeaponAimSystem (implements VehicleTickSystem):
  onTick():
    for each Aimable part in parts:
      computeAim(part, targetPoint)
      part.driveImmediate(yaw, pitch)

当前散落在:
  MachineGunBaseBlockEntity.driveImmediate()
  ShotgunBaseBlockEntity.driveImmediate()
  MachineGunTargetC2SPacket.handle()
```

#### 行动 6：System 级性能分析器

把 `AffiliationRegistry` 中的慢查询日志模式推广：

```java
// 在 VehicleSystemDispatcher 中：
long start = System.nanoTime();
system.onTick(subLevel, parts);
long elapsed = System.nanoTime() - start;
if (elapsed > 100_000) { // >100μs
    logSlowQuery(system.name(), elapsed);
}
```

### 4.3 远期（3 月+）

#### 行动 7：车辆内部消息总线

当 System 数量达到 5+ 个时，System 之间会有通信需求（比如"武器开火" → "HUD 更新弹药" → "动画播放"）。此时引入一个轻量的 `VehicleEventBus`：

```java
public class VehicleEventBus {
    private final Map<Class<?>, List<Consumer<?>>> handlers = new ConcurrentHashMap<>();

    public <T> void register(Class<T> eventType, Consumer<T> handler) { ... }
    public <T> void post(T event) { ... }
}

// 每个 SubLevel（载具）一个 bus
subLevel.getData(VehicleEventBus.class).post(new WeaponFiredEvent(weaponId));
```

实现不复杂——`ConcurrentHashMap<Class<?>, List<Consumer>>` 就够了。

#### 行动 8：社区素材包框架

你们的路线图有（⭐⭐⭐）。合适的时机是：
1. System/Part 架构稳定
2. 物理参数已数据化
3. 至少有两类不同物理属性的轮胎/武器

不满足这些前提时做素材框架 = 给移动靶心画靶。

#### 行动 9：完整 ECS 迁移（可选）

## 5. 落地示例：System/Part 架构的完整实现

本节给出可直接复制的代码骨架，帮助你快速将设计文档转化为编译通过的 Java 类。

> **设计原则**：
> - 最小侵入——不要求所有 BE 立即迁移到 PartBlockEntity
> - 渐进采用——System 可与现有 BE 共存，逐步替换
> - 轻量——不加框架依赖，纯 Java 接口 + NeoForge 事件

### 5.1 接口定义

以下三个接口对应三个 Tick 阶段：

```java
// ============================================================
// core/system/VehicleTickSystem.java
// 逻辑 Tick：20Hz，服务端，用于瞄准/控制输入/变速箱/状态更新
// ============================================================
package com.hainabaichuan75.iac_p.core.system;

import dev.ryanhcode.sable.sublevel.ServerSubLevel;
import net.minecraft.world.level.block.entity.BlockEntity;
import java.util.List;

/**
 * 载具逻辑 Tick System。
 * <p>
 * 在服务端 {@code LevelTickEvent.Pre} 中调度。适合：
 * <ul>
 * <li>瞄准目标计算</li>
 * <li>变速箱换挡逻辑</li>
 * <li>控制输入处理</li>
 * <li>状态更新与同步</li>
 * </ul>
 */
@FunctionalInterface
public interface VehicleTickSystem {

    /**
     * 每逻辑 tick 调用一次。
     *
     * @param subLevel 当前 SubLevel（服务端）
     * @param parts    该 SubLevel 内收集到的所有 Part BlockEntity
     */
    void onTick(ServerSubLevel subLevel, List<BlockEntity> parts);
}
```

```java
// ============================================================
// core/system/VehiclePhysicsSystem.java
// 物理 Tick：Sable 步进频率（~100Hz），用于悬挂力/弹簧/引擎扭矩
// ============================================================
package com.hainabaichuan75.iac_p.core.system;

import dev.ryanhcode.sable.api.physics.handle.RigidBodyHandle;
import dev.ryanhcode.sable.sublevel.ServerSubLevel;
import net.minecraft.world.level.block.entity.BlockEntity;
import java.util.List;

/**
 * 载具物理 Tick System。
 * <p>
 * 在 {@code SablePostPhysicsTickEvent} 之前调度（物理步进前施加力）。适合：
 * <ul>
 * <li>悬挂弹簧力与阻尼</li>
 * <li>轮胎驱动力与抓地力</li>
```

```java
 * 将 NeoForge 事件路由到已注册的 VehicleSystem。
 * <p>
 * 注册方式：在 {@link IACP} 或 {@link IACPClient} 的构造器中调用
 * {@code NeoForge.EVENT_BUS.register(new VehicleSystemDispatcher())}。
 */
public class VehicleSystemDispatcher {

    // ============================================================
    //  逻辑 Tick（服务端 LevelTickEvent.Pre）
    // ============================================================
    @SubscribeEvent
    public void onServerTick(LevelTickEvent.Pre event) {
        Level level = event.getLevel();
        if (level.isClientSide()) return;

        SubLevelContainer container = SubLevelContainer.getContainer(level);
        if (container == null) return;

        List<VehicleTickSystem> systems = VehicleSystemRegistry.getTickSystems();
        if (systems.isEmpty()) return;

        // 遍历所有 SubLevel
        for (SubLevel sl : container.getAllSubLevels()) {
            if (!(sl instanceof ServerSubLevel serverSL)) continue;

            // 收集该 SubLevel 内的 Part BlockEntity
            List<BlockEntity> parts = collectParts(serverSL, level);
            if (parts.isEmpty()) continue;

            // 依次调用每个 System
            for (VehicleTickSystem system : systems) {
                long start = System.nanoTime();
                system.onTick(serverSL, parts);
                long elapsed = System.nanoTime() - start;
                if (elapsed > 100_000) { // 超过 100μs 记录慢查询
                    IACP.LOGGER.warn("[Perf] Slow VehicleTickSystem: {} took {}μs",
                            system.getClass().getSimpleName(), elapsed / 1000);
                }
            }
        }
    }

    // ============================================================
    //  物理 Tick（SablePostPhysicsTickEvent 之前）
    // ============================================================
    @SubscribeEvent
    public void onPrePhysicsTick(SablePostPhysicsTickEvent event) {
        // 在物理步进前施加力
        // 注意：SablePostPhysicsTickEvent 在物理步进之后触发。
        // 如果需要在物理步进前施加力，需要监听 ForgeSablePrePhysicsTickEvent
        // 或参照 Sable 的事件文档。这里作为示例展示结构。
    }

    // ============================================================
    //  工具方法
    // ============================================================
    private List<BlockEntity> collectParts(ServerSubLevel subLevel, Level level) {
        // 使用 SubLevelScanner 或 ComponentRegistry 收集部件
        // 当前简化实现：通过 ComponentRegistry 获取所有部件的 BE

        // 需要扩展一个按 SubLevel UUID 查询所有部件的方法。
        // 临时方案：直接遍历所有 ComponentHost 的已知索引。

        return parts;
```

### 5.4 第一个 System：WeaponAimSystem

这是一个真实的 System 示例，展示如何将原本散布在多个 BE 中的瞄准逻辑集中管理：

```java
// ============================================================
// content/system/WeaponAimSystem.java
// 第一个生产级 System——统一管理所有武器的瞄准
// ============================================================
package com.hainabaichuan75.iac_p.content.system;

import com.hainabaichuan75.iac_p.affiliation.ComponentRegistry;
import com.hainabaichuan75.iac_p.affiliation.ComponentRole;
import com.hainabaichuan75.iac_p.ecs.system.VehicleTickSystem;
import dev.ryanhcode.sable.sublevel.ServerSubLevel;
import net.minecraft.world.level.block.entity.BlockEntity;
import net.minecraft.world.phys.Vec3;

import java.util.List;
import java.util.UUID;

/**
 * 武器瞄准 System。
 * <p>
 * 职责：
 * <ul>
 * <li>从 ComponentRegistry 查找该载具下所有 MACHINE_GUN_BASE / TURRET_TEST 部件</li>
 * <li>如果部件实现了 Aimable 接口，计算并驱动瞄准角度</li>
 * <li>目标点从 VehicleAimTargetCache 读取（由网络包写入）</li>
 * </ul>
 * <p>
 * 取代之前散布在 MachineGunBaseBE 和 ShotgunBaseBE 中的 driveImmediate 逻辑。
 */
public class WeaponAimSystem implements VehicleTickSystem {

    @Override
    public void onTick(ServerSubLevel subLevel, List<BlockEntity> parts) {
        UUID vehicleUUID = subLevel.getUUID();

        // 1. 读取目标点（由 MachineGunTargetC2SPacket 写入的缓存）
        Vec3 target = VehicleAimTargetCache.getTarget(vehicleUUID);
        if (target == null) return;

        // 2. 查找所有武器部件
        //    使用 ComponentRegistry 替代全量扫描
        //    注意：如果部件已经实现 Aimable，可以直接在 parts 列表中用 instanceof 过滤
        for (BlockEntity part : parts) {
            if (part instanceof Aimable aimable) {
                aimable.aimAt(target);
            }
        }

        // 3. 回退方案：如果 parts 列表不全，从 ComponentRegistry 补查
        //    var weapons = ComponentRegistry.getComponents(vehicleUUID, ComponentRole.TURRET_TEST);
        //    for (var entry : weapons) { ... }
    }
}
```

```java
// ============================================================
// content/system/VehicleAimTargetCache.java
// 车辆瞄准目标点缓存——由网络包写入，System 读取
// ============================================================
package com.hainabaichuan75.iac_p.content.system;

import net.minecraft.world.phys.Vec3;
import javax.annotation.Nullable;
import java.util.Map;
import java.util.UUID;
import java.util.concurrent.ConcurrentHashMap;

/**
 * 每辆车的瞄准目标点缓存。
 * <p>
 * 写入方：MachineGunTargetC2SPacket.handle()（客户端→服务端的命中坐标）
 * 读取方：WeaponAimSystem.onTick()（每逻辑 tick 读取）
 * <p>
 * 使用 ConcurrentHashMap 保证线程安全。
 */
public final class VehicleAimTargetCache {

    private static final Map<UUID, Vec3> TARGETS = new ConcurrentHashMap<>();

    /**
     * 更新目标点。
     *
     * @param vehicleUUID 载具 SubLevel UUID
     * @param target      目标点世界坐标
     */
    public static void setTarget(UUID vehicleUUID, Vec3 target) {
        TARGETS.put(vehicleUUID, target);
    }

    /**
     * 读取目标点。
     *
     * @param vehicleUUID 载具 SubLevel UUID
     * @return 目标点世界坐标，无目标时返回 null
     */
    @Nullable
    public static Vec3 getTarget(UUID vehicleUUID) {
        return TARGETS.get(vehicleUUID);
    }

    /**
     * 清除目标点（下车时调用）。
     */
    public static void clearTarget(UUID vehicleUUID) {
        TARGETS.remove(vehicleUUID);
    }

    private VehicleAimTargetCache() {}
}
```

## 6. 常见问题

### Q1：System/Part 架构和现有的 ComponentRegistry 是什么关系？

**互补关系**，不冲突。

- `ComponentRegistry`：运行时索引——回答"这辆车有哪些部件？"
- `VehicleSystemRegistry`：逻辑注册——回答"有哪些 System 要跑？"
- `PartBlockEntity`：部件基类——让 BE 自动被索引

**典型协同流程**：

```
WeaponAimSystem.onTick():
  1. 读 VehicleAimTargetCache 获取目标点
  2. parts 列表中用 instanceof Aimable 过滤 → 驱动瞄准
  3. 如果 parts 不全 → 补查 ComponentRegistry.getComponents(vehicleUUID, TURRET_TEST)
```

### Q2：这个架构会增加复杂度吗？

**短期会，长期降低**。

- 短期：多了一层调度器和接口定义
- 长期：新功能的开发路径从"从零写一个 BE + 摸清事件顺序"变成"实现一个 System 接口 + 注册"
- 关键在于**渐进采用**——不让现有 BE 立刻迁移，新功能按 System 写，旧功能逐步外抽

### Q3：System 调度器把 20Hz 逻辑 Tick 和 ~100Hz 物理 Tick 分开，会引入同步问题吗？

是的，这是**最大的设计挑战**。两个 Tick 频率不同、线程可能不同，System 之间共享状态需要小心：

```java
// 推荐模式：System 之间通过 SubLevel 的 Data 共享状态
// VehicleTickSystem（20Hz）写入目标扭矩
subLevel.getData(StorageKey.TORQUE).setTarget(500.0);

// VehiclePhysicsSystem（~100Hz）读取目标扭矩
double torque = subLevel.getData(StorageKey.TORQUE).getTarget();
```

或者使用 `volatile` / `AtomicReference` 实现无锁的单写入-多读取模式。

### Q4：一定要用 PartBlockEntity 吗？现有的 BE 怎么办？

**不强求**。现有 BE 可以在 System 中被直接调用，只要它们实现了 System 需要的接口（如 `Aimable`）。`PartBlockEntity` 是便利基类而非强制要求。

```java
// 现有 BE 也可以被 System 使用：
if (part instanceof ComponentHost host && host.getComponentRole() == ComponentRole.TURRET_TEST) {
    // 即使 part 不是 PartBlockEntity，也可以在这里驱动它
}
```

## 7. 总结

### 一句话

> **IAC-P 正在从"胶水模组"演化为"载具游戏微引擎"。帮助这个演化有参照系、有优先级、有落地路径，是本文的目的。**

### 核心行动

| 时间 | 行动 | 预期效果 |
|------|------|---------|
| **本周** | 写出 VehicleSystemRegistry + 三个接口 + 调度器 | 架构从文档变成代码，验证"System 跑在 BE 之上"的模式 |
| **本周** | 合并 BE 类型索引 | 减少新方块注册的认知开销 |
| **本月** | 抽出第一个真实 System（WeaponAimSystem） | 验证 System 架构在真实场景中的效果 |
| **本月** | 开始 TireType 注册表 | 打破"所有车共用一套物理常数"的限制 |
| **本季** | 全部物理参数数据化 | 玩家/服务器可调参，不同轮胎有不同特性 |
| **远期** | 社区素材包框架 | 让社区贡献纹理/特效/音效 |

### 不想做的事（明确不做的）

| 别做 | 原因 |
|------|------|
| 完整的 ECS 框架（Entity-Component-System from scratch） | 你们只需要 System/Part 两层，不需要通用的 Entity 抽象 |
| 自己的渲染管线 | 有 Minecraft + Flywheel + GeckoLib 就够 |
| 替换 NeoForge 的事件总线 | 你们的 VehicleEventBus 只需要做车辆级别的过滤，不需要替换全局总线 |
| 物理引擎抽象层（包装 Sable） | Sable API 已经干净，等 System 架构稳定后再看是否需要薄封装 |
